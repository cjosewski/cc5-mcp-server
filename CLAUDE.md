# CC5 MCP Server — Project Context

## Overview
An MCP server that lets LLMs such as Claude operate Reallusion Character Creator 5 (CC5) through natural language.

## Architecture

```
LLM (Claude) <--stdio--> MCP Server (Node.js) <--HTTP:5101--> CC5 Plugin (Python) <--RLPy--> CC5
```

## How startup works (important)

### Auto-start flow (normal operation)

```
CC5 starts
  → auto-detects OpenPlugin/CC5_MCP_Bridge/main.py
  → checks rl_plugin_info (CC5 compatibility check)
  → calls initialize_plugin()
    → bridge_server.start_server(port=5101) starts the HTTP server
    → registers process_command_queue on a QTimer(16ms)
    → bridge_server.start_image_watch() registers CC5's image-load callback (F-104; uninitialize_plugin unregisters it)
  → the bridge starts listening on http://127.0.0.1:5101
```

**Three conditions required for auto-start:**
1. An `initialize_plugin()` function in `main.py` (CC5 naming convention; `load_plugin` does not work)
2. An `rl_plugin_info = {"ap": "iClone", "ap_version": "8.0"}` dictionary in `main.py` (CC5 runs on the iClone 8 engine)
3. The plugin is installed in `OpenPlugin/CC5_MCP_Bridge/`

**Common problems and fixes:**
- `load_plugin` → CC5 ignores it. Always use `initialize_plugin`
- `PySide6` → CC5 uses PySide2. Fails silently with an import error
- Missing `from __future__ import annotations` → type-hint errors on Python 3.8 (CC5 5.13 runs 3.8.8, F-96: see "Key technical information")
- Flask dependency → CC5's Python has no Flask. Use stdlib `http.server`

### Watchdog (auto-recovery)

A server health check is built into the QTimer callback:
```python
def _check_server_health():
    if _server_thread is not None and not _server_thread.is_alive():
        _server_thread = bridge_server.start_server(port=BRIDGE_PORT)
```
→ Even if the HTTP server thread crashes, it is automatically restarted on the next QTimer tick

### Modal dialogs (queue guard)

While CC5 shows a modal dialog, the 16 ms QTimer fires inside that dialog's nested event loop, so a command would run under the dialog: under the "Unsaved project data found" crash-recovery prompt that means before the user has decided whether the unsaved scene comes back, inside an event loop RLPy calls are not made for (CC5 crashes during FBX exports were traced to sessions that most likely had that prompt open). `process_command_queue` therefore leaves the next command queued while `_describe_modal()` reports a dialog, and after `MODAL_WAIT_SECONDS` (5 s) fails it with the dialog's title and text. The 5 s count from the first tick that saw the dialog (the queued command's `modal_since`), and a tick with no dialog open drops that stamp (batch F review #0): a capture or OBJ replace the F-104 gate keeps first in the queue (see "How viewport capture works") gets its own 5 s for a later dialog instead of failing at once (a server.py change; live check pending). The guard only runs while no MCP command runs, so no MCP command waits on that dialog: the error says it is probably the user's own or CC5's and to ask the user (`_modal_dialog_error`); a progress window reads "CC5 is busy" and a dialog whose text could not be read goes to the user too (C2 review). The actions in `MODAL_SAFE_ACTIONS` (the silent head-export steps, the export/mixer status reads and `exec_python`) still run. Who answers the recovery prompt is set when CC5 starts (Chad, 2026-10-05, flight 01 F-52: "Having Claude run this autonomously is part of the problem"): with `CC5_RECOVERY_ANSWER=cancel` (or `ok`) the dialog lane clicks that button as soon as the prompt appears (`_auto_answer_recovery`, only during the first `RECOVERY_WATCH_SECONDS`, only a prompt whose text was read), records it, and `get_cc5_dialog` reports it. `scripts/cc5-restart.ps1` (the launcher Claude uses) sets `cancel` by default (`-RecoveryAnswer ask|ok|cancel`). Unset, or any other value, is `ask`: the user answers it in CC5, as for a CC5 started by hand.

Every message that shows a dialog's text (the queue guard, the waiting error, `job_status`, `get_cc5_dialog`, `check_cc5_connection`) comes from `_describe_modal`, which replaces licence serials and keys in the title and the labels with `(serial)` (`_redact_secrets`; live, SkinGen's About box showed the licence serial). A serial in a label of its own is caught too (P-4): the label after one that is only a serial or licence label is replaced whole, and the joined text is redacted once more. A readable window with no buttons that is not a progress window (that About box) is no question: the queue guard names it by its title, else its first line, and says to close it in CC5, since no MCP tool can (F-85, Batch D; live-checked 2026-10-06). Nor is a window whose buttons are QML items (F-99, batch F): live, CC5's Export FBX dialog (IC::CFbxExportDialog) is one QQuickWidget whose only button widget is the title bar's unlabelled close button, and it read "Buttons: none found". `_describe_modal` sets `buttons_unreadable` when a window has no labelled button and a child that inherits QQuickWidget or QWindowContainer; the guard then says 'CC5 has a window open whose buttons this bridge cannot read: "<title, else first line>" - answer or close it in Character Creator 5 (no MCP tool can click its buttons), then try again.', and `answer_cc5_dialog` refuses it with the same words (live check pending). `_is_window_to_close` and `_window_to_close_text` in server.py hold the rule and the words for both kinds and for the Welcome page. The MCP server words these windows as the guard does (F-94: `isWindowToClose`, `isAnsweredOnlyInCC5` and `formatDialog` in src/tools/dialog.ts, used by `get_cc5_dialog`, `check_cc5_connection` and the open-dialog checks of a recipe, a batch and `check_fit`; dialog.test.ts checks its sentences against server.py, review #10): 'CC5 has a window open with no buttons: "<title, else first line>" - close it in Character Creator 5 (no MCP tool can close it).', the QML sentence above, and for an untitled window without text CC5's Welcome / What's New page (or another untitled CC5 window), with the tip to tick "Don't show this again" (live, that page had come out as a question to ask the user about). Each caller adds its own next step, and a job waiting in the window gets a line saying to read its result with `job_status` once the window is closed. The crash-recovery prompt stays a question even when its buttons could not be read (live check pending), and a window whose text could not be read is never one to close (it may be that prompt): `get_dialog` now sends `text_read`, and the MCP server words it as the guard does, 'its text could not be read, so ask the user to answer it in CC5' (review #8).

### Dialogs a command opens (dialog lane)

CC5 often asks before doing what a command asked: a plain confirmation, or a choice (live: a second `.ccEye` load asked "The target object layer already exists ... Replace / Material Only / Cancel"). The command then waits inside that dialog's nested event loop. On each nested timer tick `_note_command_dialog` records the dialog (title, label text, buttons) in `_command_dialogs`; after `DIALOG_REPORT_SECONDS` (1 s) the waiting HTTP call returns 409 `{state: "waiting_for_dialog", job_id, dialog}` and the command's result goes to `_jobs` (read it with `job_status`). `get_dialog`/`answer_dialog` (`DIALOG_ACTIONS`) run on a separate `dialog_queue`, even while a command runs: they touch only Qt widgets, never RLPy. The lane and the dialog watch run on **their own 50 ms QTimer** (`main._dialog_timer` → `server.process_dialog_lane`): Qt never re-fires a timer while its own callback is still running, so the 16 ms command timer is silent while a command it started waits in a dialog (live: with one timer, neither the report nor `get_cc5_dialog` ran). A job waiting on a dialog reports it through `/jobs/status` (`dialog`, `dialog_message`), so recipe steps and job tools stop and show the question instead of "still running". So does a job queued behind it (`blocked_by`: it has not started, and runs after the answer, or once a window to close is closed; C2b review: a recipe's later steps each waited 120 s and then said "still running"). A command's own progress window (a `QProgressDialog`, or a dialog whose only button is Cancel) is not treated as a question: `get_dialog` marks it `progress: true` (the tools then say "CC5 is busy"), and `answer_dialog` refuses to click its Cancel, because that aborts the running command (flight 01 F-56: an export's progress window was reported as a question). The bridge writes failed requests only (`BridgeHandler.log_message`) to `%LOCALAPPDATA%\CC5_MCP_Bridge\requests.log` (beside the token file; `requests.log.1` past 1 MB), never to stdout (F-57, F-63: prints from HTTP threads reached CC5's console and a running exec_python's output).

What a waiting caller is told (batch F). Every dialog view the MCP server gets (`get_dialog`, the 409, `/jobs/status`, `answer_dialog`'s reply) comes from `_dialog_view`: title, text, buttons and `text_read`, plus `buttons_unreadable` when set; `get_dialog` adds `progress`. A command waiting in a window `answer_cc5_dialog` cannot answer (no buttons: F-84's bake opened SkinGen's About box; QML buttons, F-99; the untitled Welcome page) gets the guard's words with its job in place of "then try again" (`_waiting_dialog_error`, reviews #7 and #19; until batch F it said "Buttons: none found ... answer it with answer_cc5_dialog"): 'CC5 has a window open with no buttons: "<name>" - close it in Character Creator 5 (no MCP tool can close it). The command is still running as job <id>: read its result with job_status("<id>") once it is closed.'. A dialog whose text could not be read says 'its text could not be read, so ask the user to answer it in CC5', and a job queued behind a window to close 'runs once that window is closed'. Each text keeps the `job_status("<id>")` that `jobIdFromWaitingText` reads and a prefix `isBlockedByDialog` knows. For an older plugin's text, the MCP server words such a window as `get_cc5_dialog` does (`jobDialogMessage` in src/jobs.ts: the pending replies of `load_asset`, `bake_skin_textures` and every job tool, `job_status` (also for a job queued behind such a window), and the recipe and batch WAIT lines). `answer_dialog` records each click on the job whose command waits in the dialog (F-98): `/jobs/status` returns `answers` [{button, title}], oldest first, the button as its plain label; the startup recovery answer and buttons clicked in CC5 itself are not recorded. Recipes and batches read them, and so do `load_asset` and `job_status` (batch F reviews #8, #28): `job_status` labels a finished job answered Cancel "Cancelled in CC5 (<action>):" and replies with an error. A load gets `load_asset`'s cancelled reply ("Asset load cancelled: <path> for <target> (<words>)", the words as for a recipe step, see "What recipe and batch reports say"); any other job its JSON and "CC5's question (the "<title>" window) was answered 'Cancel', so CC5 may not have done what was asked.", or for `export_for_unity` and `export_textures` "..., so CC5 may not have written the FBX as asked: check it before using it." (a timeline note then gets `TIMELINE_LEFT_LINE`, never "The FBX is usable"). The other job tools' own replies do not read `answers`: their waits stop at the first question, so the answer comes later, through `job_status`.

`answer_dialog` fails closed: it refuses the recovery prompt wherever its words sit (title or any label), except with the one button `CC5_RECOVERY_ANSWER` names, refuses a dialog whose text could not be read and a window whose buttons are QML items (F-99), and leaves plugin-driven dialogs (`_PLUGIN_DRIVEN_TITLES`, e.g. "Create Mixer Assets" during `create_actor_mixer`'s dry run) to their own tool. Its optional `expect` (words from the question) refuses a dialog that does not contain them, so an answer cannot land on the next dialog. The button is clicked directly, in the same call that found it (`_click_now`). Live (CC5 5.13, PySide2 5.15.0a1), two deferred clicks (`QTimer.singleShot(0, <python callable>)`, then a kept-alive single-shot `QTimer`, both behind `shiboken2.isValid`) were reported as made but never reached CC5's `QMessageBox`; a direct `click()` from a timer callback answered it at once. If a click opens another dialog, the dialog lane waits in that one until it is answered in CC5.

Answering rule (Chad, 2026-10-05): Claude answers a plain confirmation of exactly what the user asked for and says so; for a real choice it shows the question and buttons with a recommendation and lets the user pick. A question nobody has answered stops a recipe or batch, and Claude runs nothing else until it is answered (D1); Replace / Material Only has no standing answer: the user picks the first one in a build, and Claude answers later identical ones in that build (one character, or one batch call) with that choice and says so (D3). CC5's "Applying this content will deactivate the current SkinGen session. Would you like to continue?", which a content load during a SkinGen session can ask (F-91, see "Change report"), is a plain confirmation of a load the user asked for: Claude answers OK and says so (`SKINGEN_QUESTION_RULE`). The rule goes with that question when an MCP command waits in it: the waiting reply of `load_asset`, every job tool and `job_status` (`withSkinGenRule` in src/jobs.ts; not for a window answered only in CC5), the report of a recipe or batch stopped on it, and `get_cc5_dialog`, `check_cc5_connection` and the open-dialog checks of a recipe, a batch and `check_fit` (`formatDialog`), which add it only with a waiting job (batch F review #12: a question no MCP command waits in may come from the user's own load in CC5, and that reply says to ask the user). `answer_cc5_dialog`'s description carries it, the `create_character` prompt says the same, and the server instructions have no room left for it. The rules the server sends at session start are in `src/prompts/content-rules.ts`.

Recipes and batches stop on questions (Chad, 2026-10-06). D1: a CC5 question nobody has answered stops `apply_character_recipe` and `batch_generate_patients`; nothing more is sent to CC5, and the report gives the question and the `continue_after` call. A question that may still be open stops them too (RB-1): `awaitJob` hands back the question the job's last poll reported when its wait runs out (`STILL_ASKING_NOTE` in src/jobs.ts: it may be a newer window), and `layerDialogHandler` stops when a carried answer's click failed and the dialog check (`checkDialog`) could not be made, instead of waiting blind. A step whose command waits in the question finishes after the answer (`continue_after` waits for its job); a step that could not run behind a dialog runs again on continuation. Where a run stopped lives in `src/build-session.ts`, in the MCP process: a restart forgets it, and the continuation is refused. D3: the first Replace / Material Only in a build goes to the user; their button, passed as `layer_answer` with `continue_after`, answers the identical question (`LAYER_EXPECT`) for the rest of that build only (one character in `create_character`, one batch call in `batch_generate_patients`; `layer_answer` itself covers one recipe call and its continuations, or the rest of one batch). A Cancel is not carried (`layer_answer` takes only Replace and Material Only): after a Cancel the run goes on with `continue_after` and no `layer_answer`, and the next identical question goes to the user again (RB-6; `CANCEL_NOT_CARRIED` in src/prompts/content-rules.ts). A recipe, a batch and `check_fit` do not start while CC5 shows a dialog or a progress window (`openDialog`: a 3 s check on the dialog lane; a failed check counts as none), and a continuation is refused the same way, except for the question its own stopped job waits in. A direct call queued behind a command that waits in a dialog never starts: after the bridge's 30 s it gets 504 `{state: "cancelled"}` "Timed out before CC5 started the command" (`dialogStopFromError`). With a window open at that moment it is a stop (the step never ran, the stop names the window, and `continue_after` runs it again; a recipe's base step as a whole); with none open it is an ordinary failure. Use `apply_character_recipe` for body and face; presets, hair and clothing go in one at a time with `load_asset`, each shown with captures and an undo offer (TS-9: `PRESET_RULE` and the `create_character` prompt ask for that, and in one recipe an undo of an early load would first take back the later steps).

What recipe and batch reports say (batch F). A step that waits in a window `answer_cc5_dialog` cannot answer is worded for it (reviews #19 and #3; `waitKind` in src/recipe.ts, `answerOrClose` in src/tools/batch.ts): a recipe's head says CC5 "has a window open with no buttons that nobody has closed yet" (or "whose buttons this bridge cannot read, and nobody has answered or closed it yet"), its go-on lines say "once the window is closed" (or "answered or closed"), a batch's head says "CC5 is waiting in a window nobody has answered or closed yet", and `continue_after` while the window is still open replies "Answer or close it first". A step waiting in a dialog whose text could not be read (review #8; it may be the crash-recovery prompt) keeps the question's head and "after the answer", its advice starts "Ask the user to answer that question in Character Creator 5: its text could not be read, so answer_cc5_dialog refuses it", and `continue_after` while it is open replies "Ask the user to answer it in CC5 first" (recipe and batch). A step a window kept from running (it never started) reads "Stopped at <step>: it could not run while CC5 had a window open (a question nobody has answered, a window to close in CC5 because it has no buttons or this bridge cannot read its buttons, or a progress window), so nothing after it was sent to CC5." and "Still to run / To go on once the window is answered or closed in CC5", as a batch words that stop (batch F review #10; it said "after the answer"). In the WAIT line of a step CC5 started, the plugin's words sending the agent to `job_status` for that step's own job read "continue_after reads its result" (batch F review #29: the advice below says not to call `job_status`); words about a job it is queued behind stay. A step whose job's `answers` hold a Cancel (F-98) reads "CANCELLED <step> (<words>)" and is counted apart ("1 of 2 steps was cancelled in CC5; 1 succeeded.", never "All N steps succeeded"). The words claim only what is known (batch F review #11): "answered Cancel in CC5, so CC5 applied nothing" for a content load whose own before/after comparison ran in full and found nothing (`comparedNothing` in src/change-report.ts: complete, no material out of time, no WARNING note, no fact); "answered Cancel in CC5, but CC5 still changed what the lines below say", with its CHECK and NOTE lines, when the comparison saw changes; for the base step "answered Cancel in CC5, so CC5 may not have done it; any characters that were in the scene had already been deleted" (`CANCELLED_BASE`); else, as for a pose or a load compared in part or not at all, "answered Cancel in CC5, so CC5 may not have done it" (`CANCELLED_UNSURE`). Only Cancels clicked through `answer_cc5_dialog` are seen. In a batch a cancelled recipe step other than the base step, or a cancelled export ("export: CC5's question ... was answered 'Cancel', so CC5 may not have written the FBX as asked: check it before using it"), makes the variant FAIL with its FBX kept. A variant whose base load failed or was answered Cancel is not exported, and the batch goes on: the batch's own base load ("FAIL <v>: base load: CC5's question (...) was answered 'Cancel', so the base may not have loaded; this variant's recipe and export were not run", or "FAIL <v>: base load failed: <error>") or its recipe's base step ("FAIL <v>: not exported: its recipe's base step was cancelled (<words>), so the scene may not hold its base", or "failed (<error>)"). This holds after `continue_after` too (batch F review #7): a continuation whose stopped base load then failed or was answered Cancel is no longer refused as a changed scene (the scene clear or base step had deleted every character), while one whose base load finished normally still needs exactly one character in the scene. A recipe's base step shows `delete_avatar`'s notes in its line ("OK   base: CC5's selection (Pants) was cleared before the delete: ..."), also after `continue_after`; a refused delete (F-92, fail closed) ends the recipe with no `continue_after`: "Ended at base: that step failed, so nothing after it was sent to CC5.", "Not sent to CC5: <steps>." and the advice to run `clear_selection` (or deselect everything in CC5) and the whole recipe again. A batch refused at its scene clear, or at a variant recipe's base step, stops before that variant is exported, with no `continue_after` ("Stopped at <variant> (scene clear): CC5 refused to delete a character in the scene, ..."; to go on, clear the selection and run the variants not finished again). Under each variant's line the batch reply lists, indented (F-100): `delete_avatar`'s notes, each question the batch answered itself and with what, each failed or CANCELLED step and why, and one line on the injuries ("injuries 'separate': 4 overlay images and BO_Athletic_injuries.json written beside the FBX"); the manifest keeps `scene_clear` and `injuries_summary`.

### Hot reload (apply code changes immediately)

```
Edit cc5_api.py, cc5_changes.py or an extension module (cc5_pipeline.py, cc5_skin.py, cc5_builder.py,
cc5_scene.py: server.EXTENSION_MODULES) in the repo
  → copy it to the installed plugin: re-run install-plugin.ps1 (Administrator PowerShell; it copies every
    cc5-plugin/*.py, new modules included), or copy each changed or new .py into
    C:\Program Files\Reallusion\Character Creator 5\Bin64\OpenPlugin\CC5_MCP_Bridge\
    (CC5 runs that copy, not the repo; without this step /reload succeeds and changes nothing)
  → curl -H "X-CC5-Token: $(cat "$LOCALAPPDATA/CC5_MCP_Bridge/token")" http://127.0.0.1:5101/reload
    (or Claude runs it automatically; CC5 must have been started with CC5_DEV_MODE=1)
  → importlib.reload(cc5_api) and the extension modules runs; re-importing cc5_api drops cc5_changes (a helper
    load_asset imports, not an extension module) from sys.modules, so the next load imports it again
  → _auto_patch_server() updates ACTION_MAP / POST_ROUTES / GET_ROUTES
  → the new code takes effect immediately (no CC5 restart needed)
```

**Limitation:** changes to server.py (adding routes, changing validation, etc.) and main.py require re-running install-plugin.ps1 and restarting CC5.
Changes to cc5_api.py, cc5_changes.py and the extension modules take effect on reload, once the installed copy is updated.

### Troubleshooting

| Symptom | Cause | Fix |
|------|------|------|
| The bridge does not come up after CC5 starts | Entry function is not named `initialize_plugin` / `rl_plugin_info` is missing | Check the function name and dictionary in main.py |
| Cannot connect to port 5101 | Plugin not installed | Run `install-plugin.ps1` with administrator privileges |
| `curl /reload` returns 404 | An old server.py is running | Restart CC5 so it loads the new server.py |
| `curl /reload` etc. return 401 | Missing `X-CC5-Token` header / token mismatch | Send the value of `%LOCALAPPDATA%\CC5_MCP_Bridge\token` in `X-CC5-Token` (required on every route except `/health`) |
| `/reload` or `/exec/python` returns 403 | Dev mode is disabled (the default) | Start CC5 with `CC5_DEV_MODE=1` (for `/exec/python` only, `CC5_ALLOW_EXEC=1` also works) |
| RLPy function not found | CC5 version differences | Check with `hasattr()` and fail gracefully |
| Morphs have no effect | No avatar in the scene | Create an avatar first with `create_avatar` |
| Material color does not change | Wrong mesh/material name | Confirm the correct names with `get_material_info` |
| Undo does not work | Not wrapped in `BeginAction/EndAction` | Always wrap modifying operations in BeginAction/EndAction |
| Capture is a blank image | No avatar in the scene | Create avatar → apply morphs → capture |
| RenderImage fails | Can happen after loading a .ccProject | Automatically falls back to a Windows screenshot |
| Welcome dialog gets in the way | Shown when CC5 starts | Tick "Don't show this again", or close it by hand |

### Notes on subdivision (SubD / HD)

`set_subdivision_level` is strictly a tool for "switching between HD subdivision levels that have already been generated".
**Generating** the HD data itself is only possible through the CC5 UI operation `Modify > Subdivide`; it cannot be triggered from RLPy/the API.
Therefore an avatar without generated HD data has `max_level = 0` (no HD data), and this is **a normal state, not an error**.
The same applies to `sub_d_level` in `export_fbx`: a level above the character's highest subdivision level (0 without HD data) is refused.

> **Note for versions earlier than 5.07:** On CC5 builds earlier than 5.07, the SubD cache / plugin modules sometimes need to be rebuilt. Update to 5.07 or later if possible.

### export_fbx details

`export_fbx` reproduces CC5's "Export FBX (InstaLOD)" dialog using `RLPy.RExportFbxSetting`.
All parameters are optional (only `output_path` is required), preserving full backward compatibility with the existing behavior.

| Parameter | Dialog item | Description |
|-----------|--------------|------|
| `output_path` | Output destination | A file name without a directory (e.g. `character.fbx`) resolves under `D:\CC5Export` (configurable via `CC5_EXPORT_DIR`). Absolute paths are used as-is. |
| `target_tool` | Target Tool Preset | `"UE5"`/`"Unreal"` applies the Unreal-oriented flags (Y-up, UE bone axis). |
| `export_motion` | FBX Options | `true` = "Mesh and Motion" (default), `false` = "Mesh" only. Uses `EnableExportMotion`. |
| `sub_d_level` | HD Character Subdivision Level | 0/1/2. Applied via `SetExportLevel` (does not modify the scene). A level above the character's highest one (`GetMaxSubdivMeshLevel`) is refused. `set_subdivision_level` is used only in the flags-only fallback. |
| `embed_textures` | Texture Settings: Embed Textures | Adds `EExportFbxOptions_EmbedTexture`. |

### Full CC5 restart procedure

Claude asks the user before restarting CC5. Killing CC5 (`taskkill //F`, `Stop-Process`) loses unsaved work,
so the user saves and closes CC5 themselves. Nothing sends keys or clicks to CC5.

```bash
# 1. The user saves their work and closes CC5. Check that it has gone:
tasklist 2>/dev/null | grep -q "CharacterCreator" && echo "CC5 is still running"

# 2. Launch CC5 (the plugin starts the bridge automatically)
"/c/Program Files/Reallusion/Character Creator 5/Bin64/CharacterCreator.exe" &

# 3. Wait for the bridge to start (live starts took up to about 70 seconds; this waits up to 240 s, F-93)
for i in $(seq 1 120); do
  curl -s --connect-timeout 1 http://127.0.0.1:5101/health | grep -q "ok" && break
  sleep 2
done
#    No answer by then: check the CC5 window (the 3D Creator / AI Studio chooser, a startup dialog), then curl /health again.

# 4. The user answers CC5's startup dialogs in CC5 (until they do, the viewport does not render correctly):
#   a) "Unsaved project data found": OK restores the auto-saved changes, Cancel discards them
#      (started with CC5_RECOVERY_ANSWER=cancel, as cc5-restart.ps1 does by default, the plugin answers Cancel)
#      (README.md, Known issues)
#   b) Welcome screen: tick "Don't show this again", or close it by hand
```

`scripts/cc5-restart.ps1` runs steps 2-3 and prints the step 4 guidance. It stops if CC5 is still running;
`-Force` kills CC5 instead, and unsaved work is lost. Its health check ends as soon as the bridge answers and gives up
after 240 s with "The bridge did not answer within 240 s (live starts took up to about 70 s)." and "Check the CC5 window
(the 3D Creator / AI Studio chooser, a startup dialog), and check the bridge with: curl.exe http://127.0.0.1:5101/health"

### How viewport capture works
`capture_viewport` works through a three-stage fallback:
1. **RLPy.RenderImage()** — fastest; normally this succeeds
2. **ForceViewportUpdate + retry** — when RenderImage fails on the first attempt
3. **Windows screenshot (PowerShell)** — when RenderImage does not work at all, e.g. after loading a .ccProject

Note: fallback 3 copies the CC5 window's area of the screen (the whole primary screen when CC5 has no main window), so the CC5 window must be in the foreground. It runs in the plugin (`_capture_window_screenshot`). Until the C2b review it never wrote a file: its path was passed after `-Command`, where PowerShell does not bind it; the path now travels in `CC5_CAP_OUT`. Live (C2 check, called directly): it wrote a 2575x1407 PNG of the window area; not yet reached through capture_viewport's own fallback chain. It starts PowerShell with `CREATE_NO_WINDOW` (F-64, Batch D), so no console window shows in the capture (live-checked 2026-10-06).

**A capture or an OBJ replace waits until CC5 has settled (F-104, batch F).** CC5 records a render as an undo step, which the capture undoes at once (F-53). But CC5 has not finished a file load when `LoadFile` returns: it goes on loading the images (REventCallback `OnImageAsyncLoadStart` ... `OnImageAsyncLoadAllDone`), a render made then gets no step of its own, and the capture's undo took the load back (live: Box_001 gone in 6 of 7 runs with a load job and a capture queued together; the same window broke `replace_mesh_from_obj` after `load_texture`, F-101). So `process_command_queue` keeps `capture_viewport` and `replace_mesh_from_obj` (`SETTLE_ACTIONS`) at the head of the queue until 0.3 s after the previous command ended (`SETTLE_SECONDS`, also after a failed one) and while CC5 loads images, at most 20 s from its last load start (`IMAGE_LOAD_WAIT_SECONDS`). The commands behind keep their order, a cancelled head or one the queue guard fails is not held, and a held direct capture still has the bridge's 30 s. `initialize_plugin` registers the image watch after its timers (`server.start_image_watch`; `uninitialize_plugin` calls `stop_image_watch` before the server stops); a registration that fails prints one line, and then only the 0.3 s rule holds. With the gate patched into the live queue the box stayed 5 of 5 times. Behind the gate, the capture compares the scene before its render with the scene after its own undo, when one ran (`_scene_fingerprint`: the characters, the clothes, accessories and hair they wear, props, lights and cameras; never the selection, which that undo changes by itself). It sees only objects and worn items: an undo that took back a material, texture, preset or morph change (a skin or eye preset, `load_texture`) gets no redo and no note (batch F review #2). When something came or went, it redoes once and adds a WARNING to `notes` (batch F review #4): `CAPTURE_UNDO_REDONE` ("... it was put back with a redo (F-104). Check the scene.") when the scene is back, also after a redo that raised; `CAPTURE_UNDO_REDO_FAILED` ("... and the redo after it failed (F-104): redo (or Edit > Redo in CC5) can bring it back; check the scene.") when the redo raised and the change is not back, and then `redo` is not refused, since CC5's redo slot holds the change (`_redo_slots` ["user"]); `CAPTURE_UNDO_NOT_CHECKED` when the scene cannot be read after a redo that ran; `CAPTURE_UNDO_LOST` only when a redo ran and the change did not come back. A scene it cannot read before the redo is not checked. While the server's image-load watch still reports images loading (the gate let the capture run after 20 s; `_images_still_loading` reads `server._images_loading` by name), the capture does not undo its own step at all, a harmless miscount, and adds `CAPTURE_UNDO_SKIPPED` ("WARNING: CC5 was still loading images when this capture rendered, so the capture did not undo its own render step (F-104): the next undo may take back only that step; check with a capture after an undo."; batch F review #2). After a capture `redo` stays refused (F-55: its step replaced CC5's redo history), except after a failed F-104 redo. `capture_viewport` shows every note in its reply, and `check_fit` a capture's WARNING under that view; a failed capture also has its notes in `error`, one line each (batch F review #5: the bridge answers `{success: false}` with HTTP 400, of which the MCP server keeps only `error`). No help, live: one command per timer tick, waiting until Qt's event loop went idle, `BeginAction(name, bBlockRecordUndo=True)` or BeginAction/EndAction around RenderImage. A server.py and main.py change (reinstall and restart CC5); the committed gate, the capture's redo and batch F review's capture changes (cc5_api.py): live check pending.

### Change report (F-34)

Every character-content `load_asset` (`_CHARACTER_CONTENT_EXTENSIONS`), and so every preset or clothing step of a recipe or batch variant, is compared before and after; a base or scene-content load (.ccAvatar, .iProp, .ccCam) is not. `cc5_changes.py` reads the target character just before and just after `LoadFile`, in the same main-thread command. In CC5 it only reads: no undo step of its own, no render, camera or selection call; the only things it changes are the bridge's own record of colours and opacities written and its set of characters whose colour reads may be late (F-90, below). It compares the worn items by group, the shaping morphs, the subdivision level and, per material on every mesh the character lists (`GetMeshNames(True)`, worn items' meshes included): presence, shader, diffuse colour, opacity, whether the Diffuse Blend channel holds an image, and the shader parameters (padding skipped). It never reads glossiness, specular or texture weights, which are stale until CC5 renders (F-65). Each read has 2.5 s; materials not read both times are reported as not compared, and at most 300 facts are returned. `src/change-report.ts` turns the facts into lines: CHECK is what changed besides what the load was for (an item removed or added in another group, a skin colour or pallor reset by a load that is not a skin preset, an overlay gone, lower opacity, a material gone, a shaping morph, the subdivision level, or a clothing, accessory or hair load that changed nothing); Applied is what it was for (on an eye preset's load also every material change on the eye itself: CC_Base_Eye's Std_Eye_L/R and Std_Cornea_L/R, the eye occlusion and the tear line, not eyelashes, brows or glasses; F-97, live: _Blue1 Eyes' cornea opacity 1 -> 0.8 was a CHECK line); NOTE is what CC5 does after the load (the SkinGen session a SkinGen preset starts, F-91 below; none for a load that failed or was answered Cancel, which also gets no nothing-changed WARNING); NOT CHECKED is what it cannot see (the fit: check_fit; hair, brows or clothing hidden in the viewport: captures, F-91 below), parts not compared and WARNING notes. In a recipe, a preset's skin-colour or pallor CHECK line that a later `skin_rgb` or `skin_condition` step sets again becomes a NOTE ("set again by ... later in this recipe"), only when the load went to the first character, which those steps change (`changes.target_is_first`; X-1: a load on another character keeps its CHECK lines and its step names that character). A batch variant left with CHECK lines is FAIL "exported, but check with the user" and keeps its FBX (Chad's DEC-4, option a, 2026-10-06). `CC5_CHANGE_CHECK=0` (or false, no, off) in CC5's environment switches the comparison off, and every load then says so; it is only for a person debugging: Claude and cc5-restart.ps1 never set it. An older plugin gives "the installed CC5 plugin predates the change report". Pictures judged by code are pending (F-34-phase2).

CC5 reports a material's diffuse colour as it was when it last rendered (F-90, live 2026-10-07). Right after `set_skin_color(0.5, 0.5, 0.5)`, `GetDiffuseColor` read 1.0, also after `RGlobal.ForceViewportUpdate()`, after `RGlobal.ObjectModified(avatar, EObjectModifiedType_Material)` and in the next bridge command; one capture made it read 0.502. So the read before a load missed a colour set since the last render, and the load got its CHECK line (a recipe's `skin_rgb` (0.8, 0.6, 0.5), then Sport Sneakers: "CHECK skin colour ... (1, 1, 1) -> (0.8, 0.6, 0.502)"). The bridge therefore records every diffuse colour and opacity it writes and CC5 accepts (`cc5_api._writes_since_render`, keyed by character id, mesh and material; colours on the 0-255 steps CC5 reads after a render, opacity 0-1 at 3 decimals; whether CC5 also reports opacity late is not known): `set_diffuse_color`, `set_skin_color`, `set_lip_color`, `set_hair_color` (a hair item's materials under the character, through which the comparison reads them), `set_skin_condition` and `set_material_opacity`. `load_asset` passes the record to `cc5_changes.begin`. For a recorded field the comparison reports nothing when the read after the load is the value written (CC5 caught up), and the change from the value written when it is another value. When it is still the read from before (A == B != written), the read says nothing about the load (a load that reset the field to the colour CC5 still reported would go unseen; review #1), so one NOT CHECKED line says so (`NOT_REFRESHED`): "WARNING: CC5 still reports the colour from before the bridge set it on <materials>, so whether this load changed it was not checked: capture, then compare" (at most 12 materials named). After the comparison a field leaves the record (`_settle`) when CC5 reads it fresh, and also when it is still read as before (batch F review #3): the bridge then no longer knows what CC5 holds there, and kept, the record would answer `get_diffuse_color` and the export's tint read with a colour the material may not have; the character is marked (below). A material the character no longer lists leaves too. A capture whose `RenderImage` wrote the file (`capture_viewport`, and so `check_fit`) empties the record, and so do `undo` and `redo`; the window-screenshot fallback does not. After an undo or redo CC5's reads may still give the colours of its last render (review #20; inferred, not seen live), so `undo` and `redo` add the characters in the scene to `_colours_late_since_undo`, a set of character ids (none when CC5 cannot list them), and such a capture empties it; a load whose comparison still read a recorded field as before adds its character too. A load on a marked character reports colour and opacity differences on fields the bridge has no record of as one NOT CHECKED line instead of CHECK or Applied lines (`COLOURS_LATE`, batch F review #14: "WARNING: CC5 may report material colours late after an undo, a redo or a load that left a colour unsettled (seen for a colour set without an undo, F-90; not checked live after an undo), so whether this load changed the <fields> on <materials> was not checked: capture, then compare"); a character loaded after the undo (a recipe's base, a batch variant's new character) is not marked and is compared as read. The record and the set survive `/reload` and are lost on a CC5 restart; recorded fields and unrecorded materials are otherwise compared as before. The record answers two other reads (review #0): `get_diffuse_color` gives a colour the bridge set since the last render from it, with the note `DIFFUSE_FROM_RECORD` on the line after the RGB, and `export_for_unity`'s skin-tint read (`cc5_skin._read_tint`: the injuries report and the sidecar's `tints`) uses it too, so a colour just set or just cleared counts. Without a record both read CC5, and on a marked character they say it may be late (batch F review #3): `get_diffuse_color` adds `DIFFUSE_READ_MAY_BE_LATE` ("CC5 may report this colour as it was at its last render: an undo, a redo or a load since then may have changed it, and CC5 reports a material's colour only after it next renders. Live check pending.

A SkinGen or makeup preset hides worn items in the viewport (F-91, live): `Red Velvet.ccSkinGenPreset` on Kevin hid the hair, the brows and all clothing, while `list_hair` and `list_clothes` still listed every item, an export still contained them, and `set_item_visible(Shirt, true)` reported success and changed nothing. Deleting a prop also ended a session, without a question; a load with no session asks nothing; whether another SkinGen preset loaded during a session asks is not tested. So a SkinGen preset's load report gets one NOTE line, worded as seen (`SKINGEN_SESSION_NOTE`, batch F review #13: "... until a later content load or a delete ends it (live: a prop delete ended it without a question). A content load during the session can ask ... (seen for a prop load): for a load the user asked for, answer OK and say so."). `load_asset` and `job_status` show it, also with an older plugin, and a recipe report shows it as "     NOTE ..." under the step; a load answered Cancel gets none, and the batch reply does not show it (the manifest's steps keep it in `loadNotes`). That question is a plain confirmation of a load the user asked for: Claude answers OK and says so (`SKINGEN_QUESTION_RULE`, which says CC5 "can ask" it; see "Answering rule"). `PRESET_RULE` names the session in the server instructions and in `load_asset`'s description ("a SkinGen or makeup preset hid hair, brows and clothing until a content load or a delete ended its SkinGen session"; its old "a lip makeup preset ... reset the skin colour" is gone: the batch D check read the skin colour unchanged after that preset).

### Fit check (F-44)

`check_fit` (src/tools/fit.ts) frames the character and captures each view (default face, left, right, back, front; front is sent as `home`) at 1280x720 into `%TEMP%\cc5_fit\check_<time>`, keeping the newest 20 checks, and returns every image with its view, path and a reading rubric. It detects nothing by itself and never says a fit is clean. A capture that is not 1280x720 is the window-screenshot fallback, so the check stops INCOMPLETE there, as at any view it cannot frame or capture, and sends nothing more. Identical consecutive images are flagged. It is refused while a recipe or batch runs or a dialog is open. Each capture undoes its own step, and the camera stays on the last view; a capture's WARNING notes (F-104) go under that view's label, or with the reason when the check stops INCOMPLETE there (a failed capture's error carries them, batch F review #5). Fit corrections are pending (F-44-phase2).

### Skin overlays and skin conditions in Unity (F-75)

An FBX carries neither a Diffuse Blend overlay nor the skin shader's pallor offsets. `export_for_unity` exports a character that has them only with the user's `injuries` choice (`bake`, `separate` or `omit`; no default), and every reply lists what the FBX does not carry. It names each overlay's image from the bridge's own record (`cc5_pipeline.BLEND_SOURCES`, written by `load_texture` and `apply_skin_overlay`); `cc5_api.undo` and `redo` mark every record stale (`mark_blend_sources_stale`, P-1), and a stale record, or one at 0% while CC5 reads more, never overrides CC5's read and its image is neither shipped nor baked (a WARNING line asks to apply it again).
README.md, "Skin overlays and skin conditions in Unity", has the choices, the sidecar fields, the batch rules and the calibration status.

## Key technical information

- **CC5 Python**: Python 3.8.8 + PySide2 (not PySide6!). Live (F-96, 2026-10-07): `sys.version` read "3.8.8 (tags/v3.8.8:024d805, Feb 19 2021, 13:18:16) [MSC v.1928 64 bit (AMD64)]", and CC5's crash dumps load python38.dll. So the plugin may use no Python 3.9+ feature: the Python tests run under the developer's Python (3.14), where such a feature passes, while inside CC5 a syntax error stops the whole plugin. `tests/py/test_py38_compat.py` therefore reads every `cc5-plugin/*.py` and refuses a fixed list of such features, not every one (batch F review #32): syntax the 3.8 grammar refuses (also decorators that are not a dotted name or a call of one, and, checked on Python 3.12+, f-strings with the f-string's own quote, a backslash or a comment inside `{...}`, or a line break inside a single-quoted f-string's `{...}`); outside annotations, `[...]` on a builtin generic (`list`, `dict`, `tuple`, `set`, `frozenset`, `type`) or on `collections.*`, `collections.abc.*`, `queue.Queue`, `re.Pattern` or `re.Match` (also through an import alias), a `|` with a builtin type, `None` or a typing name (`Any`, `Optional`, `Union`, `Callable`, `List`, ...; bare, as `typing.X` or through an alias) on either side, and any `|` in the classes `isinstance()` or `issubclass()` takes (reviews #15, #22: before batch F only builtin names were caught; RLPy flag ORs stay allowed); `str.removeprefix`/`removesuffix`, `functools.cache`, `math.lcm`, `zoneinfo`, `graphlib`, `zip(strict=...)`, and a `|` or `|=` with a dict display, dict comprehension or `dict()` call; a module with annotations but no `from __future__ import annotations` (its one find, main.py, has the import now). Two dict variables, or two classes outside `isinstance()`/`issubclass()`, joined with `|` pass, and so does a 3.9+ library name not on its list (`tomllib`, `itertools.pairwise`): keep to 3.8 by hand too
- **RLPy**: NOT thread-safe — must run on the main thread via QTimer
- **Bridge**: `http.server` (no Flask) on port 5101
- **QTimer**: 16ms interval (~60fps) — tuned for responsiveness
- **Plugin function names**: `initialize_plugin` / `uninitialize_plugin` (`load/unload` does not work)
- **Type-hint compatibility**: `from __future__ import annotations` is required in every plugin module with annotations (Python 3.8; `test_py38_compat.py` checks it)
- **Morph value range**: [-1.0, 1.0] (negative values shrink the feature)
- **morph ID cache**: automatically invalidated when the avatar changes

- MCP server instructions: SERVER_INSTRUCTIONS (src/prompts/content-rules.ts) is sent at initialize (src/index.ts); Claude Code shows it at session start and cuts it at about 2,000 characters, so a test keeps it at or under 2,000 (since batch F review #13 it is exactly 2,000: any addition needs a cut elsewhere); the same rule constants feed the tool descriptions.
- Live smoke test: `py -3 scripts/live_smoke_test.py` against a running CC5 (it changes the scene: use a scratch project). It puts the first light's colour and multiplier back in a `finally` and checks that ("light colour and multiplier set back"), and judges `exec_python` by the bridge's answer: 200 with 42 when CC5 allows it, 403 when CC5 runs without dev mode (batch E's check failed whenever CC5 ran with `CC5_DEV_MODE=1`).
- A new tool file is registered in src/index.ts, and the counts in README.md and CLAUDE.md are updated (tests/index-wiring.test.ts checks them).
- Bridge authentication: every route except `/health` requires the `X-CC5-Token` header. The token is generated at `%LOCALAPPDATA%\CC5_MCP_Bridge\token` the first time the plugin starts (can be overridden with the environment variable `CC5_BRIDGE_TOKEN`). The MCP server sends it automatically
- Hot reload: `curl -H "X-CC5-Token: $(cat "$LOCALAPPDATA/CC5_MCP_Bridge/token")" http://127.0.0.1:5101/reload` (re-imports the installed cc5_api.py, cc5_changes.py and extension modules; requires `CC5_DEV_MODE=1`, returns 403 when disabled)
- API discovery: `curl -H "X-CC5-Token: $(cat "$LOCALAPPDATA/CC5_MCP_Bridge/token")" http://127.0.0.1:5101/api`
- CC5 restart: ask the user to save and close CC5 (never kill it), then `scripts/cc5-restart.ps1` (see "Full CC5 restart procedure") → the bridge starts automatically

## Environment variables

| Variable | Default | Description |
|------|-----------|------|
| CC5_BRIDGE_URL | http://127.0.0.1:5101 | Bridge endpoint URL |
| CC5_BRIDGE_PORT | 5101 | Bridge port (for start_bridge.py) |
| CC5_BRIDGE_TOKEN | (empty = use the token file) | Bridge authentication token (`X-CC5-Token`). Must be set to the same value in both the plugin and the MCP server |
| CC5_DEV_MODE | 0 | Dev mode (1/true/yes enables /reload and /exec/python) |
| CC5_ALLOW_EXEC | (empty) | 1/true/yes enables /exec/python even when dev mode is disabled |
| CC5_RECOVERY_ANSWER | (empty = ask) | cancel/ok: the plugin answers CC5's "Unsaved project data found" prompt with that button at startup and records it (get_cc5_dialog). Set by scripts/cc5-restart.ps1 (default cancel) |
| CC5_REQUEST_TIMEOUT_MS | 35000 | Request timeout (ms) |
| CC5_ROOT | (auto-detected) | CC5 install path |
| CC5_CHANGE_CHECK | (empty = on) | 0/false/no/off switch off the before/after load comparison (F-34). Read by the plugin, so set it in CC5's environment before launch. Only for a person debugging: Claude and scripts/cc5-restart.ps1 never set it, and while it is set every load says the comparison is off |
